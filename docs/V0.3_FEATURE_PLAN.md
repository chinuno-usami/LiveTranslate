# v0.3 功能实施计划：按源输出路由 / 自定义快捷键 / SteamVR 手势定位

> 目标版本：v0.3.0
> 状态：计划（尚未实施）
> 涉及需求：
> 1. 不同输入源分别设置是否输出到桌面端 / OSC / SteamVR
> 2. 可自定义全局快捷键
> 3. SteamVR Overlay 支持用手势移动字幕面板（跟随头部 / 世界坐标两种锚点），并可锁定位置避免误触发
>
> 结论摘要：
> - 需求 1、2 改动集中、风险低，可在现有架构上直接实现。
> - 需求 3 技术可行，但必须接受 SteamVR 的两层限制：默认不能独占输入；若要在操作浮窗时屏蔽游戏输入，需要采用 SteamVR Input 2.0 的 overlay-global action set priority（XSOverlay 同款方案），并要求用户开启 SteamVR 实验设置。建议先做一次 Windows + 真机 spike，再决定最终手势组合与默认锁定位。
>
> **本版修订（实现前评审反馈）**
> - 需求 3 拆成「3C 核心层」（legacy 读手柄 + 锁定 + 抓取 + 持久化）与「3A 输入屏蔽层」（Input 2.0 + app 注册 + 默认 bindings）。**3C 与 3A 均纳入 v0.3.0**；按 S1（3C）→ S2（3A）顺序实施，3A 决策门不通过时需回到确认，不静默砍功能。
> - 修正字段假设：`SteamVrConfig` 当前没有 `horizontal_offset_m`，`hmd_matrix` 把水平偏移硬编码为 0，必须新增字段并改写 transform。
> - 明确 `writer::set_sources` 必须同步写入新字段，否则 `verify_change_applied` 会直接报错。
> - 补充拖动值 clamp、快捷键录制暂停全局快捷键、OSC 通道清屏、SteamVR app 注册与 zip 打包、版本号/发布项等遗漏。

## 0. 结论与优先级

| 需求 | 可行性 | 主要改动 | 风险 | 建议优先级 |
| --- | --- | --- | --- | --- |
| 1. 按源路由输出 | 高 | 配置字段 + 字幕视图过滤 + 三个输出分别取快照 | 低：标签语义、旧配置兼容 | P0 |
| 2. 自定义快捷键 | 高 | `[hotkeys]` 配置 + 运行时注册/重注册 + 设置页录制控件 | 中：系统占用、平台差异、重复绑定 | P1 |
| 3. SteamVR 手势移动 | 3C 核心：可行；3A 输入屏蔽：可行但成本高 | 3C：VR 线程轮询手柄 + 射线/近距离抓取 + 位置换算 + 锁定 + 持久化；3A：SteamVR Input 2.0 action manifest + 默认 bindings + app 注册 + overlay-global priority | 3C 中：`horizontal_offset_m` 缺失、拖动值需 clamp、Dashboard 下不可拖；3A 中高：manifest/默认 bindings、SteamVR 实验设置、可能需 `ApplicationType::Overlay`、打包必须带 `steamvr.vrmanifest` | P2（3C 与 3A 均纳入 0.3.0，按 S1→S2 顺序） |

建议实施顺序：**1 → 2 → 3C → 3A（纳入 0.3.0）**。需求 1 会顺带重构输出快照路径，需求 3C 的状态/锁定又依赖需求 2 的快捷键体系，所以这个顺序依赖最少。

> 工期口径：需求 1+2 约 4–5 天；需求 3C 约 5–7 天；需求 3A 约 5–7 天（含 app 注册、默认 bindings、4 类手柄与真机矩阵）；发布/文档约 0.5–1 天。**合计 14–20 天**，这是含 3A 的 0.3.0 交付口径。

> 交付边界：3C 与 3A 都属于 0.3.0 范围。3A 在运行期不可用时自动降级为 3C 并在状态里说明；但**如果 spike 决策门不通过，不允许静默砍功能**，必须回到 §9 的待确认项（改用 `ApplicationType::Overlay`、改路线 B 或调整版本范围）。

## 1. 现状与关键约束

### 1.1 当前数据流

```
每个启用输入源 run_source
  └─ AudioCapture → resample → VAD/固定分片 → ASR → 可选翻译
       └─ PipelineEvent::Subtitle(SubtitleLine { source_id, label, source, translated })
            └─ Forwarder（单任务串行）
                 ├─ SubtitleState（一份历史，含所有源）
                 ├─ 桌面：SubtitlePayload → subtitle://update
                 └─ OutputManager.publish(snapshot)
                       ├─ SteamVR Overlay
                       └─ OSC / VRChat Chatbox
```

### 1.2 必须保留的兼容性

- 旧 `config.toml`（没有新区段、没有源输出字段）必须直接启动，行为和 v0.2 一致。
- 旧配置语义：所有源默认输出到全部三个通道。
- `[[audio.sources]]` 为空时仍由 `audio.device_name` 合成 `id = "default"` 的单源，且该源默认全通道输出。
- 不破坏现有托盘、点击穿透、窗口几何、配置档、热更新和采集重启逻辑。
- 标准版（无 `steamvr` / `osc` feature）仍然能编译、运行；相关字段保留但忽略。

### 1.3 明确非目标

- 不做 per-source 的 ASR 后端 / 翻译模型；路由只影响「显示/发送」，不影响识别与翻译。
- 不做 per-source 的输出格式（例如某源只发原文）；本期只控制是否发送。
- 不实现无手柄手部追踪（Quest hand tracking / OpenXR 手骨架）；手势指手柄按键 + 姿态。
- 不实现 VR 内的设置菜单 / 键盘；锁定开关通过桌面设置、全局快捷键或 VR 手势完成。
- 不做 SteamVR Dashboard 注册，也不做 VR 内输入法。
- 需求 3 分两层，避免把可选能力混进核心路径：
  - **3C 核心层**：只用 legacy `GetControllerStateWithPose` + `device_to_absolute_tracking_pose` 完成锁定、组合抓取、移动与持久化；**不承诺屏蔽游戏输入**。
  - **3A 输入屏蔽层**：引入 SteamVR Input 2.0 action manifest、默认 bindings、`steamvr.vrmanifest` app 注册与 overlay-global priority。**3A 纳入 v0.3.0 交付**（受 SteamVR 实验设置限制）；运行期不可用时自动降级为 3C 并提示。若 spike 决策门不通过，不允许静默降级，必须回到 §9 待确认项。

## 2. 需求一：按输入源路由输出

### 2.1 配置设计

在 `AudioSourceConfig` 增加三个布尔字段，默认 `true`：

```toml
[[audio.sources]]
id = "mic"
label = "麦克风"
device = "mic:0"
enabled = true
translate = true
language = ""
# 新增：输出路由。默认全部 true，旧配置不写也等价于 true。
desktop = true
osc = true
steamvr = true

[[audio.sources]]
id = "game"
label = "游戏声音"
device = "loopback:0"
enabled = true
translate = true
language = ""
# 典型场景：桌面显示两边；OSC / VR 只发麦克风
desktop = true
osc = false
steamvr = false
```

Rust 侧：

```rust
#[derive(Debug, Clone, PartialEq, Serialize, Deserialize)]
pub struct AudioSourceConfig {
    // ... 现有字段
    #[serde(default = "default_true")]
    pub desktop: bool,
    #[serde(default = "default_true")]
    pub osc: bool,
    #[serde(default = "default_true")]
    pub steamvr: bool,
}
```

设计取舍：

- 选择三个显式布尔而不是 `outputs = ["desktop", "osc"]`：TOML 可读性更好，设置页勾选框也更直接。
- 字段名放在源表内部，不会和 `[output.osc]` / `[output.steamvr]` 区段冲突。
- `AudioSourceConfig::new()` 默认全部 `true`；`effective_sources()` 合成的旧单源也全部 `true`。

### 2.2 视图模型：一份历史，多通道投影

不要让三个输出各自维护一份 `SubtitleState`，否则历史、去重、`max_lines` 会不同步。保留一份历史，按通道做「渲染前过滤」。

核心 API：

```rust
// src/subtitle/mod.rs
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum OutputChannel {
    Desktop,
    Osc,
    SteamVr,
}

/// 某个通道允许出现的 source_id 集合
pub struct ChannelFilter {
    pub channel: OutputChannel,
    pub allowed: std::collections::HashSet<String>,
}

impl ChannelFilter {
    pub fn allows(&self, source_id: &str) -> bool {
        self.allowed.contains(source_id)
    }
}

impl SubtitleState {
    /// 只渲染该通道允许的源，并按该通道的可见源重新判定 Auto 标签。
    pub fn display_lines_for(&self, filter: &ChannelFilter) -> Vec<DisplayLine>;
}
```

`SubtitleState` 中把 `active_labels: Vec<String>` 改为：

```rust
active_sources: Vec<(String, String)>, // (source_id, label)
```

原因：标签 Auto 判定必须知道「可见且正在运行的源」有几个。只存 label 无法和 `source_id` 过滤结果对齐。

标签规则：

- `LabelMode::Always`：只要该条进入当前通道，就带 `[label]`。
- `LabelMode::Never`：从不带。
- `LabelMode::Auto`：
  - 当前通道内「可见且正在运行」的源 ≥ 2 → 加；
  - 或当前通道历史里出现 ≥ 2 个不同 `source_id` → 加；
  - 否则不加。
- 这样当 OSC 只保留麦克风时，不会出现无意义的 `[麦克风]` 前缀；桌面仍同时出现两个源时会自动带前缀。

由配置构建过滤器：

```rust
impl AudioSourceConfig {
    pub fn routes_to(&self, channel: OutputChannel) -> bool {
        match channel {
            OutputChannel::Desktop => self.desktop,
            OutputChannel::Osc => self.osc,
            OutputChannel::SteamVr => self.steamvr,
        }
    }
}

pub fn channel_filter(config: &AppConfig, channel: OutputChannel) -> ChannelFilter {
    let allowed = config
        .audio
        .effective_sources(config.translate.enabled)
        .into_iter()
        .filter(|s| s.routes_to(channel))
        .map(|s| s.id)
        .collect();
    ChannelFilter { channel, allowed }
}
```

兼容边界：历史里可能存在已从配置删除的 `source_id`。过滤时按「不在 allowed 里」处理，因此它会从所有通道消失；这是符合预期的，等历史滚动后自然清理。

### 2.3 输出层改造

`OutputManager::publish` 改为两个独立快照：

```rust
pub fn publish(&self, steamvr: &[DisplayLine], osc: &[DisplayLine]) {
    if !self.capture_active.load(Ordering::SeqCst) {
        return;
    }
    self.steamvr.publish(steamvr);
    self.osc.publish(osc);
}
```

理由：

- OSC 的 `publish` 会「用快照重建内部 history」，传过滤后的快照即可保证被排除的源不会残留在 Chatbox。
- SteamVR 的 `publish` 会覆盖最新快照，传过滤后的结果即可。
- 两个 sink 已经是非阻塞的，接口变化不会影响流水线。

**OSC 清屏补充**：当前 `OscSink` 的滚动历史在快照为空时不会发送空串（`pack()` 返回 `None`，`pending_text` 也不会置空），所以「把 OSC 通道的源全部取消勾选」后 Chatbox 会保留旧文本直到客户端超时。需求 1 需要额外处理：

- 在 `OscSink` 中记录上一次 filtered snapshot 是否非空；当「非空 → 空」时，无视 rolling 去重发一次空串（与 `set_capture_active(false)` 的清屏路径一致）。
- 或者给 `publish` 增加 `force_clear_when_empty` 语义，由 `OutputManager` 在路由变更时显式触发。
- SteamVR 不需要额外处理：空快照会让 `has_visible_text = false`，走淡出/隐藏分支。

`main.rs` 中集中生成三份视图：

```rust
struct SubtitleViews {
    desktop: Vec<DisplayLine>,
    osc: Vec<DisplayLine>,
    steamvr: Vec<DisplayLine>,
}

fn subtitle_views(state: &SharedState, config: &AppConfig) -> SubtitleViews {
    let state = state.subtitle_state.lock();
    SubtitleViews {
        desktop: trim_last(
            state.display_lines_for(&channel_filter(config, OutputChannel::Desktop)),
            config.subtitle.max_lines,
        ),
        osc: trim_last(
            state.display_lines_for(&channel_filter(config, OutputChannel::Osc)),
            config.output.osc.max_lines,
        ),
        steamvr: trim_last(
            state.display_lines_for(&channel_filter(config, OutputChannel::SteamVr)),
            config.output.steamvr.max_lines,
        ),
    }
}
```

需要同步修改的调用点：

- `src/main.rs` 的 `PipelineEvent::Subtitle` 分支：先生成 `views`，再分别 `emit SUBTITLE_EVENT(views.desktop)` 和 `outputs.publish(&views.steamvr, &views.osc)`。
- `publish_subtitle_snapshot`：配置热更新、输出开关、保存设置后都走同一套视图。
- `emit_subtitle_with_config` / `emit_subtitle`：桌面浮窗只发 `desktop` 视图。
- `src/app.rs` 控制台模式：`handle_console_event` 增加 `config: &AppConfig` 参数，用同样的 `channel_filter` 生成 OSC/SteamVR 视图（控制台没有桌面窗口，但仍应尊重 OSC/VR 路由）。
- `desktop_entries` 保留为 `trim_last` 的桌面特化，或直接改成通用 `trim_last`。

### 2.4 热更新

需求 1 的路由字段全部是热字段，不应该触发采集重启。

当前 `apply_settings_changes` 对 `audio.sources` 无条件 `restart = true`，需要改成「按字段差量判断」：

```rust
fn sources_need_restart(old: &AppConfig, new: &AppConfig) -> bool {
    // 需要重启的源字段：身份（增删源）、设备、启用状态、展示名
    // 不需要重启：desktop/osc/steamvr/translate（以及 language，已有 watch 热更新）
    // 注意：audio.max_active_sources / vad.* / asr.* 仍由 schema 的 restart_required 负责，
    // 不要把它们混进 source 级 diff，否则去掉 `restart = true` 后会漏重启。
    ...
}
```

- `id` 变化（增删源重新匹配）→ 重启。
- `device` / `enabled` → 重启（`device` 建议先按 `canonical_device_spec` 归一化，避免 `mic` ↔ `mic:0` 这种等价写法触发无谓重启）。
- `label` → 重启（`SourceContext.label` 在源任务启动时被 clone，运行中的字幕事件仍用旧标签）。可选优化：在 forwarder 用 registry 的 label 覆盖 `SubtitleLine.label`，即可把 label 也变成热字段；本期不做。
- `translate` / `desktop` / `osc` / `steamvr` → 不重启。
- `language` → 不重启（`SourceRegistry::sync_config` 会通过 `language_tx` 热更新）。
- 顺序调整 → 不重启（`sync_config` 会重新排序 registry）。

保存设置后：

1. `apply_hot_config` 更新 `SubtitleState` 的 `max_lines` / `show_source` / `label_mode`；
2. 从 registry 重新同步 `active_sources`（避免源改名后标签仍用旧值）；
3. `publish_subtitle_snapshot` 用新路由重新生成三个视图；
4. 如果 `sources_need_restart` 为真且采集在跑，才执行停止/启动。

`save_config_raw` / `reload_config` / `switch_profile` 目前只要在跑就重启。**不要直接把这三条入口换成只比较 `audio.sources` 的 helper**：它们还可能修改 VAD / ASR / 采样率 / 切片时长等冷字段，只比 sources 会出现「保存成功但没重启、新配置未生效」。建议：

- `save_settings` 用 `sources_need_restart` 做细粒度（schema 已有 per-field `restart_required`）；
- `save_config_raw` / `reload_config` / `switch_profile` 保留无条件重启，或实现一个覆盖 `schema::is_restart_required` 全部冷字段的 `cold_fields_changed(old, new)` 并配测试；
- `switch_profile` 若做差量，需在 `profiles::switch_to` 之前用已解析的 `new` 计算 diff（当前代码是先 stop 再 switch）。

该项作为需求 1 的附带优化，可延后，不影响主流程。

### 2.5 设置页与浮窗 UI

输入源表格（`tauri-ui/settings.js` 的 `renderSourcesBlock`）新增三列/一组勾选：

```
ID | 展示名 | 设备 | 语言覆盖 | 翻译 | 启用 | 桌面 | OSC | VR | 排序/删除
```

- 新增行默认 `desktop = osc = steamvr = true`。
- `markSourcesDirty` 仍然把整个 `audio.sources` 数组标脏，保存时由后端 serde 解析三个新字段。
- `validateSources` 增加提示：
  - 启用的源如果三个输出都没勾选 → 允许保存，但显示黄色提示「该源只写入历史，不会出现在任何输出」。
  - 其余校验不变。
- 表格列较多，需要同步调整 `settings.css` 的 `sources-table` 列宽；移动端/窄窗口可以改为每行两行布局，或把三个勾选框放到一个「输出」单元格里（推荐后者，节省宽度）：

```
输出
☑桌面  ☑OSC  ☐VR
```

浮窗的输入源 popover 不增加路由编辑，只在 tooltip/状态里显示摘要，例如 `麦克风 · 桌面/OSC`。如果觉得信息噪声大，可以第一版不显示，只在设置页管理。

如果要做这个摘要，需要同步扩展 `SourceStatusItem`（和/或 `ActiveSourcePayload`），把 `desktop/osc/steamvr` 带到前端；`OverlayConfigPayload` 目前不含 sources。

> 语义边界（已确认）：本期的「桌面端」只指浮窗字幕流（`subtitle://update`），**不包含翻译历史窗口、输入源 popover**——后两者始终显示全部源。停用（`enabled = false`）的源仍保留在 `effective_sources` 中，已有历史会继续显示在允许它的通道，直到自然滚出；只有从配置里删除的 `source_id` 才会立即从所有通道消失。

### 2.6 配置写入与原始 TOML

- `src/config/writer.rs` 的 `SOURCE_KEYS` 增加 `desktop`、`osc`、`steamvr`，否则原始配置编辑器会把它们当作未知键提示。
- **`writer::set_sources` 必须显式 `update_table_scalar` 写入 `desktop` / `osc` / `steamvr`**（当前只写 `id/label/device/enabled/translate/language`）。只靠复用旧表残留键有两个问题：新增源/改 id 时新字段丢失；`verify_change_applied` 对 `audio.sources` 做全量比较（`cfg.audio.sources == expected`），带 `osc = false` 的新源会直接报「写入后结果或顺序不一致」。
- `verify_change_applied` 的新字段不是「自动生效」，而是依赖上一条的 `set_sources` 补写；需要补测试覆盖：新增源 `osc = false`、旧表原地编辑、重排/改 id 三种路径。
- `config/default.toml` 的示例源补上三个字段和注释。
- `schema.rs` 的 `sources_table` 是自定义组件，不需要为每个输出字段单独建 schema field；但 `schema::build` 的输入源分组说明要更新。
- `AudioSourceConfig::new()`（代码内构造）与 `effective_sources()` 的旧单源合成也要显式给出三个 `true`，避免 Default 演化后漏字段。

### 2.7 边界与测试

单测：

- `effective_sources` 合成的旧单源三个输出均为 `true`。
- `SubtitleState::display_lines_for`：
  - 两个源，Desktop 全允许 → 两条且带 `[A]` / `[B]`；
  - OSC 只允许 A → 只有 A，且 Auto 模式不加前缀；
  - 不可见源不出现在结果里；
  - `Always` 在只有 A 时仍带前缀；
  - 历史里混合 A/B、当前只允许 A 时，不因历史里的 B 触发前缀。
- `trim_last` 对三个通道分别按各自的 `max_lines` 裁剪。
- `writer::unknown_keys` 不再把 `audio.sources[0].osc` 等识别为未知键。
- `writer::set_sources` 落盘后回读：新增源带 `osc = false` / `steamvr = false` 能保存成功；旧表原地编辑不丢字段；改 id/重排后新字段仍在。
- 路由使某通道变空时，OSC sink 收到空快照并能主动清屏（见 §2.3 的 OSC 清屏补充）。
- 采集未运行时修改路由，不 panic、不重启；下次 start 后按新路由输出。

手工验收：

1. 麦克风 + `loopback:0` 同时启用；桌面两个都勾选，OSC / VR 只勾麦克风。
2. 初始化后桌面同时滚两条；OSC 只出现麦克风内容；VR 只出现麦克风内容。
3. 运行中在设置页取消麦克风的 OSC 勾选并保存 → OSC 不再更新；不出现「采集中断/重启」；桌面和 VR 不受影响。
4. 重新启动程序后路由保持。
5. 旧配置文件（无新字段）启动后三个输出仍然显示所有源。
6. 某个源三个输出都不勾选时仍能识别、仍写历史，只是不上任何输出。
7. 把 OSC 通道的所有源都取消勾选并保存 → OSC Chatbox 的旧内容应被清掉（而不是等 VRChat 超时）。
8. 停用一个正在输出字幕的源 → 它的历史仍按 §2.5 的语义显示；删除该源后才立即从所有通道消失。
9. 采集停止状态下修改路由，再启动采集 → 三端都按新路由输出。

### 3.1 现状

| accelerator | 功能 |
| --- | --- |
| `CmdOrCtrl+Alt+S` | 显示浮窗 |
| `CmdOrCtrl+Alt+R` | 开始采集 |

### 3.2 配置设计


```rust
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct HotkeyConfig {
    #[serde(default = "default_hotkey_show")] pub show: String,
    #[serde(default = "default_hotkey_start")] pub start: String,
    #[serde(default = "default_hotkey_stop")] pub stop: String,

    #[serde(default = "default_hotkey_click_through")] pub toggle_click_through: String,
```

动作语义（避免新增字段没有实现）：

| 动作 | 行为 | 是否落盘 |
| --- | --- | --- |
| `show` / `open_settings` / `open_history` / `quit` | 复用现有窗口/退出函数 | 否 |
| `start` / `stop` | 复用 `start_capture_bg` / `stop_capture_bg` | 否 |
| `toggle_capture` | 依据 `state.pipeline.is_running()` 选择 start/stop | 否 |
| `toggle_click_through` | 复用 `toggle_click_through`（已有 `config_update` 锁保护） | 是 |
| `toggle_translate` | 复用 `set_mode`/`set_translate_enabled` 的路径，切换并持久化 `translate.enabled` | 是 |
| `toggle_steamvr_lock` | 读写 `output.steamvr.gesture.locked`，经 `update_and_persist_config` 后调用 `outputs.apply_config` | 是（需求 3C 需明确定义） |

不在本期的动作（例如逐源开关）不预留字段，避免空实现。

### 3.3 运行时注册与重注册

新增一层封装（建议放 `src/hotkeys.rs`，注册动作仍由 `tray.rs` 执行）：

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum HotkeyAction {
    Show, Start, Stop, ToggleCapture, ToggleClickThrough,
    Settings, History, ToggleTranslate, ToggleSteamvrLock, Quit,
}

pub struct HotkeyStatusItem {
    pub action: String,
    pub label: String,
    pub accelerator: String,
    pub registered: bool,
    pub error: Option<String>,
}
```

注册流程：

```text
apply_hotkeys(app, config):
  1. lock hotkey_lock（串行化，避免两次保存并发 unregister/register）
  2. manager = app.global_shortcut_manager()
  3. manager.unregister_all()（失败只 warn，不中断）
  4. for action in HotkeyAction::ALL:
       acc = config.hotkeys.get(action)
       if acc.trim().is_empty(): continue
       根据 action 生成 handler（捕获 app.clone()）
       match manager.register(acc, handler):
         Ok  -> status.registered = true
         Err -> status.registered = false, error = Some(e)；继续注册其余项
  5. 更新 SharedState.hotkey_status
  6. emit hotkey-status://update + 如有失败 emit NOTICE_EVENT
```

要点：

- **一个失败不能影响其它快捷键**：逐个注册，保持现有的「一个组合被占用，不能让后面的退出键一起失效」原则。
- `unregister_all` 后重新注册会有一个极短的空窗，可以接受；注册动作应放在后台任务，不阻塞 UI。
- 重注册触发点：启动 `setup`、`save_settings`、`save_config_raw`、`reload_config`、`switch_profile`。统一接到 `apply_hot_config`。
- 启动时需要主动执行一次 `apply_hotkeys` 并在主窗口就绪后 emit `hotkey-status://update`，否则浮窗/设置页首次打开拿不到「未生效」状态。
- `get_hotkeys()` 必须读 `state.config()`（运行态），不能重新读磁盘：降级态/预览态下两者可能不同。
- 配置格式错误在保存前由 `validate()` 拒绝；「格式合法但被系统占用」属于运行期失败，保存成功 + 界面提示，不自动回滚（否则用户无法保存一个暂时冲突的配置）。

### 3.4 配置校验

`AppConfig::validate()` 增加：

- 所有非空 accelerator 归一化后不能重复。归一化同时处理大小写、修饰键顺序，并在当前平台上把 `CmdOrCtrl` 视为与 `Ctrl` / `Cmd` 之一等价（避免 Windows 上两个写法实际抢同一个组合）。
- 保守格式检查：
  - 不能只有修饰键；
  - 必须包含至少一个修饰键（`Ctrl/Control/Cmd/Command/CmdOrCtrl/CommandOrControl/Alt/Option/Shift/Super/Meta`），或功能键 `F1..F24`；
  - 拒绝裸字母/数字/空格等单键，避免全局抢占输入。
- 不做过度的键名白名单校验；最终能否注册以 `manager.register()` 为准，避免误杀 Tauri 支持的冷门键名。
- 兼容性：校验只作用于非空字符串，且不得因为新增校验让旧配置/旧默认值在保存时报错；若未来调整默认快捷键，需在 README 写迁移说明。

`is_restart_required` 明确对 `hotkeys.*` 返回 `false`。

### 3.5 设置页交互

Schema 增加分组：

```text
id: "hotkeys"
title: "快捷键"
custom: Some("hotkeys_actions")  // 只用于渲染「恢复默认」按钮/提示
fields: [show, start, ...] 每个都是 FieldKind::Hotkey
```

新增 `FieldKind::Hotkey`，前端渲染：

```
[ Ctrl + Alt + S          ]  [录制] [清除]
```

录制逻辑：

- **进入录制前必须先暂停所有全局快捷键（已确认，含退出键）**：调用 `apply_hotkeys` 的暂停路径（`unregister_all` 且不重新注册），否则按到当前已注册的 `CmdOrCtrl+Alt+Q` 会直接退出应用、按到 `S` 会弹窗。录制结束/取消后，用**当前已保存的配置**重新注册（不能把录制中的半成品写进去）。
- 暂停范围覆盖 `quit`，不保留例外；录制 UI 需显示「快捷键已暂停」提示，避免用户误以为按键失灵。
- 点击「录制」进入捕获状态；窗口级 `keydown` 捕获，`preventDefault` / `stopPropagation`，并阻止 Space/Enter 激活当前聚焦按钮。
- 按下 `Escape` 取消录制；只按修饰键不产生值。
- 使用 `event.code` 生成跨键盘布局稳定的键名：`KeyA → A`、`Digit1 → 1`、`F1..F24`、`Numpad*`、方向键、`Comma/Period/Slash/...`、`Enter/Space/Tab/Backspace/Delete/Home/End/PageUp/PageDown/Insert/Escape`。
- 修饰键组合成 Tauri accelerator：`Ctrl+Alt+S`、`Cmd+Shift+F8` 等。
- 支持手动编辑文本框（高级用户可以直接写 `CmdOrCtrl+Alt+S`）。
- 录制结束后检查当前表单内是否重复；重复就地报错，不写入 dirty。
- 「恢复默认」按钮：把全部 hotkey 字段设为默认值（只改 dirty，仍需点保存）。
- 关闭设置窗口/切走标签时若仍在录制，必须走取消路径并恢复快捷键注册。

后端提供：

```text
get_hotkeys() -> { items: [{ action, label, accelerator, registered, error }] }
```

设置页打开时拉取一次；收到 `hotkey-status://update` 时刷新「已注册 / 未生效」标记。`get_hotkeys()` 需要注册到 `invoke_handler`，并与 `hotkey-status` 事件一起在 `src/ui/overlay.rs` 定义 payload。

### 3.6 浮窗快捷键帮助

`tauri-ui/index.html` 目前是硬编码的快捷键表。改为：

- 表格体 `<tbody id="shortcut-list">`；
- `app.js` 启动时调用 `get_hotkeys()`，按 `items` 渲染；

- 空 accelerator 的项显示「未设置」；

同时把工具栏按钮的 `title`（设置页快捷键提示）改为动态值。

### 3.7 边界与测试

## 4. 需求三：SteamVR 手势移动字幕面板

### 4.1 可行性结论

**需求 3 分成 3C 核心层与 3A 输入屏蔽层：3C 用 legacy 手柄读取即可交付；3A 才需要 SteamVR Input 2.0 的 overlay-global action set priority（XSOverlay 同款方案）。**

先修正上一版计划里的说法：

- 用 legacy `GetControllerStateWithPose` 读手柄，只能「读到」，不能阻止游戏收到同一按键。
- SteamVR 从 1.10.1 起提供了一个实验性机制：overlay 应用可以把 action set 的 `nPriority` 设为 `k_nActionSetOverlayGlobalPriorityMin..Max`，让该 action set 中**已绑定**的输入源在 scene application 中失效。XSOverlay 的「Input Blocking」就是利用它。
- 因此准确说法不是「无法独占」，而是：**没有默认独占；需要 SteamVR Input 2.0 action manifest + 用户开启 SteamVR 实验设置，才能选择性地屏蔽部分/全部手柄输入**。
- **3C 不依赖以上机制**：锁定 + 组合 + 射线命中 + 持久化只用 legacy 接口，即使 3A 失败也能完整交付「用手柄移动面板」。

技术上：

- `openvr` 0.9 已封装 `system.tracked_device_index_for_controller_role`、`system.controller_state_with_pose`、`system.device_to_absolute_tracking_pose`，足以读取手柄姿态与按键。
- `openvr` 0.9 也封装了 `IVRInput`（`Context::input()`、`Input::set_action_manifest`、`get_action_set_handle`、`get_action_handle`、`update_actions`、`get_digital_action_data`），并暴露 `VRActiveActionSet` 包装 `openvr_sys::VRActiveActionSet_t`；后者包含 `nPriority` 字段。
- `openvr` 0.9 还提供 `application.add_application_manifest(path, temporary)`，可作为未注册 app 的运行时注册路径。
- `SteamVrSink` 已经有一个 33ms 的专用 VR 线程，轮询输入、更新 transform、上传纹理都在同一线程内完成，符合 OpenVR 线程亲和性。
- Overlay 的 hmd / world 两种 transform 都已存在，但**`horizontal_offset_m` 并不存在**：当前 `SteamVrConfig` 没有该字段，`hmd_matrix` 把水平偏移硬编码为 `0.0`。3C 必须新增字段、`Default`、`default.toml`、schema、validate，并改写 `hmd_matrix`，否则 hmd 模式横向拖动无法实现。

限制（必须在产品行为里体现）：

1. **输入屏蔽是「按输入源」而不是「整个手柄」**。只有绑定在高优先级 action set 里的按键/轴会被压制；没绑定的按键仍会传给游戏。XSOverlay 能看起来「屏蔽全部」，是因为它的 action manifest 声明了 23 个动作，覆盖了它用到的按键；但仍然不是硬件级全屏蔽。
2. **必须启用 SteamVR 实验设置**：`steamvr/globalActionSetPriority`（Developer → “Enable global input from overlays (experimental)”）。未开启时 priority 设置不会生效。
3. **Dashboard 优先级更高**：Dashboard 打开时，输入焦点被 Dashboard 接管，scene app 的 `GetControllerStateWithPose` / action 读取不可靠，且 overlay-global priority 也无法覆盖 Dashboard 输入。此时不能拖拽，这是可接受的。
4. **可能需要 `ApplicationType::Overlay`**：`openvr.h` 的注释明确写的是 “Overlay applications (i.e. ApplicationType_Overlay)”。当前项目用 `Background` 是为了不主动拉起 SteamVR；是否 `Background` 也能获得 global priority 必须 spike 验证。如果不行，需要在 VR 模式下改用 `Overlay` 初始化，并处理它可能自动启动 SteamVR 的生命周期差异。
5. **OpenVR 初始化是进程级单次状态**：`Context` drop 后才能重新 `init`，所以「运行期按手势开关切 Background/Overlay」意味着重启 VR worker（短暂断连）。建议启动时根据配置决定 app type，运行期改这项配置时提示重启应用，而不是动态切换。
6. 只支持手柄，不支持纯手部追踪（没有标准按键）。
7. `openvr` 0.9 没有封装 `IVROverlay::ComputeOverlayIntersection`。首版用「射线 + 平面」近似；曲面面板（`curvature > 0`）的命中点会有边缘误差，必要时再通过 `openvr_sys` 直接调用原生接口。
8. 面板只有在可见时才好抓取；因静音淡出而隐藏时，需要先产生一条字幕或由其它方式唤出。
9. **3A 需要 app 注册，而不只是一个 `actions.json`**：按 Valve/Unity SteamVR 插件与 XSOverlay 的做法，action manifest 需要配合 `steamvr.vrmanifest`（`app_key` + `action_manifest_path`）或运行时 `AddApplicationManifest` 注册；否则 `SetActionManifestPath`、默认 bindings 的自动加载、`OpenBindingUI` 都可能失败。3A 的 spike 必须先验证这一链路。
10. **manifest 与 bindings 必须是稳定的绝对路径**：SteamVR 不接受打包内的临时路径；发布包又是 zip 目录而非 Tauri bundle，不能用 `tauri.conf.json` 的 `bundle.resources` 兜底。**已确认采用 `include_bytes!` 内嵌资源，首次解压到「当前活动配置文件所在目录」下的版本化子目录**：
    - 默认（OS 用户配置）例如 macOS `~/Library/Application Support/com.chinuno.LiveTranslate/steamvr/<app_version>/`、Windows `%APPDATA%\chinuno\LiveTranslate\config\steamvr\<app_version>\`；
    - **便携模式**（exe 旁存在 `config/default.toml`）时为 `<exe_dir>/config/steamvr/<app_version>/`；
    - 开发模式（cwd 下 `config/default.toml`）时为 `<cwd>/config/steamvr/<app_version>/`；
    - 若该目录不可写（如 Program Files），回退到 `data_local_dir()/steamvr/<app_version>/`，仍失败则 3A 降级并提示。
    - 升级时按版本戳覆盖；旧版本子目录可保留一代用于回滚，之后清理。

#### 4.1.1 XSOverlay 的 Input Blocking 具体做了什么

XSOverlay 的公开设置说明与开发者回复可以拼出完整链路：

1. XSOverlay 是一个使用 SteamVR Input 2.0 action manifest 的 overlay 应用（`XSOverlay_Data/StreamingAssets/SteamVR/actions.json`，启动日志会显示 “Successfully loaded N actions from action manifest”）。
2. 它声明了覆盖自身交互的 action set/actions，并给这些 action set 设置 overlay-global priority（`0x01000000..0x01FFFFFF`）。
3. 它只在 **Layout Mode 打开**（或按 `InputBlockingBehavior` 选择「hover 到 overlay 时」）激活这些高优先级 action set；关闭 Layout Mode 后不再提交，游戏立即恢复输入。
4. 用户需要在 SteamVR 开发者设置里打开 “Enable global input from overlays (experimental)”（配置键 `steamvr/globalActionSetPriority`）。XSOverlay 的开发者明确说过：XSO 利用这个 developer option 在 Layout Mode 中接管输入。
5. 效果是：被 XSOverlay action 绑定的输入源（trigger/grip/thumbstick 等）在游戏侧绑定被禁用；未被绑定的输入仍可用。开发者原话是“taking priority over inputs that are bound on the controllers”。

Valve 对这套机制的说明（`openvr.h`）：

```cpp
// Overlay applications (i.e. ApplicationType_Overlay) may set their action set priority
// to a value between k_nActionSetOverlayGlobalPriorityMin and k_nActionSetOverlayGlobalPriorityMax
// to cause any inputs bound to a source used by that action set to be disabled in scene applications.
static const int32_t k_nActionSetOverlayGlobalPriorityMin = 0x01000000;
static const int32_t k_nActionSetOverlayGlobalPriorityMax = 0x01FFFFFF;
```

```cpp
struct VRActiveActionSet_t {
    VRActionSetHandle_t ulActionSet;
    VRInputValueHandle_t ulRestrictedToDevice;
    VRActionSetHandle_t ulSecondaryActionSet;
    uint32_t unPadding;
    int32_t nPriority; // 设为 overlay-global 区间才会压制 scene app
};
```

需要特别记住的行为细节（Valve 测试与社区反馈）：

- 这是 **button-by-button** 的优先级覆盖，不是整只手柄静音；只绑 trigger 就只压制 trigger，摇杆仍会传给游戏。
- 只对「同一输入源」生效；overlay 的 action 是 chord / advanced（double/long/touch）时，和游戏侧 simple binding 的组合可能有覆盖不到的情况。
- 高优先级 action set 也可能影响 Dashboard 的同一按键；测试时不要用 trigger 做解锁确认，避免把 Dashboard 选择键也压掉。
- 游戏使用 legacy input 时同样会被压制（Valve 的测试里 game app 是 legacy input，regular action 被 blocked）。

#### 4.1.2 实现路线与取舍

| 路线 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A. Overlay-global action set（3A，纳入 0.3.0，XSOverlay 同款） | SteamVR Input 2.0 manifest + 默认 bindings + `steamvr.vrmanifest` app 注册；移动模式下用 `nPriority = Min/Max` 提交 action set；**只绑定 grip/trigger** | 可按按键屏蔽；只压 grip/trigger，不影响摇杆/菜单；可与读取输入共用 | 需要 action manifest、默认 bindings、app 注册、SteamVR 实验设置；可能需要 `ApplicationType::Overlay`；估算 5–7 天，不是“1–2 天额外工作” |
| B. `VROverlayFlags_MakeOverlaysInteractiveIfVisible` | 在移动模式显示一个 interactive overlay（可配 `SetOverlayInputMethod(Mouse)`） | 不需要 action manifest / app 注册；实现快 | 会屏蔽**所有**输入给 scene app；SteamVR 激光指针/焦点行为不可控；可能干扰 Dashboard；不是选择性屏蔽 |
| C. 不屏蔽（3C 核心） | 只用 legacy 读手柄，靠锁定/组合防误触 | 无额外依赖，最稳 | 游戏中 grip/trigger 仍会触发游戏动作，只能降低概率 |

建议：**C（3C）与 A（3A）均纳入 0.3.0**；A 只屏蔽 grip/trigger，且只检测/提示 SteamVR 实验设置，不尝试一键修改。若 A 的 manifest/注册/绑定成本或 `ApplicationType` 问题不可接受，**不要静默砍功能**：回到 §9 待确认项，选择改路线 B、改 `ApplicationType::Overlay`，或调整版本范围。C 作为运行期降级路径（3A 初始化失败时仍可拖动）。

参考依据：

- OpenVR `openvr.h` 的 `k_nActionSetOverlayGlobalPriorityMin/Max`、`VRActiveActionSet_t.nPriority` 注释。
- OpenVR issue #1236（Valve 引入 global action set priority；说明是 button-by-button，需要 SteamVR Developer 实验设置）。
- XSOverlay 官方设置文档 “Input Blocking”：只在 Layout Mode 打开时接管输入，关闭后恢复 scene application。
- XSOverlay 开发者在 issue #96 的回复：XSO 利用 SteamVR 的 “Enable global input from overlays (experimental)” developer option；按键绑定优先级在 overlay 侧生效。
- XSOverlay 的 Steam 配置/日志显示其使用 `XSOverlay_Data/StreamingAssets/SteamVR/actions.json`（action manifest）。
- OpenVR issue #1429：`VROverlayFlags_MakeOverlaysInteractiveIfVisible` 会阻塞 scene app 输入，作为路线 B 的依据。

Spike 重点：

1. 用 `ApplicationType::Background` 初始化，设置 `globalActionSetPriority` 后，`nPriority=Min` 的 action set 是否真的能压制 scene app；如果报 `InvalidPriority`/`PermissionDenied` 或无效果，改用 `ApplicationType::Overlay` 复测。
2. 只绑定 `grip` + `trigger` 时，游戏里的摇杆/菜单是否仍然正常（验证“按输入源”而不是“整只手柄”）。
3. Dashboard 打开时 action 是否返回 inactive；关闭后是否自动恢复。
4. 退出移动模式后，游戏是否立刻恢复输入（不残留卡键）；实现上必须显式把 `nPriority` 归零，不能只依赖 SteamVR 在应用退出时清理。
5. SteamVR 设置未开启时，程序是否能检测到并给出明确提示，而不是静默失效。
6. **app 注册链路**：只调用 `set_action_manifest` 是否可行？若否，`steamvr.vrmanifest` / `AddApplicationManifest` 是否能让默认 bindings 自动加载？`OpenBindingUI` 是否能打开正确的 app？
7. **发布路径**：把 exe + manifest + bindings 放进一个 zip 解压目录（模拟 `release.yml` 产物），manifest 用 `current_exe()` 推导绝对路径，确认 SteamVR 能稳定加载（不依赖 Tauri bundle）。
8. **默认 bindings 兼容性**：knuckles / vive_controller / oculus_touch / holographic_controller 至少各验证一次「无手动绑定即可加载」；某一条非法 binding 是否导致整个 manifest 失败。

**Spike 决策门（任一不满足就砍 3A，只交付 3C）**：

- `Background` 或 `Overlay` 下至少一种能稳定获得 global priority；
- manifest + `steamvr.vrmanifest` 能在 zip 发布目录下自动加载默认 bindings；
- 退出移动模式/异常退出后不残留卡键；
- 不要求用户手动在 SteamVR 里逐项绑定（冷门手柄可降级为手动绑定，但主流手柄必须自动可用）。

如果 spike 发现后台应用读不到手柄姿态或无法使用 global priority，降级方案：

- 保留桌面设置 + 快捷键微调（方向键/按钮调整 `world_position` / 偏移），不做 VR 内手势；
- 或采用路线 B 的「全屏蔽」作为可选实验功能；
- 或只做 C（锁定+组合），不承诺屏蔽游戏输入。

### 4.2 交互设计

#### 锚点

| 模式 | 手势改变的量 | 手柄移动映射 |
| --- | --- | --- |
| `anchor = "hmd"` | `horizontal_offset_m` / `height_offset_m` / `distance_m` | 世界位移转换到 HMD 局部坐标系 |
| `anchor = "world"` | `world_position[x,y,z]` | 直接世界位移；旋转/偏航保持不变 |

两种模式共用同一套抓取逻辑；切换锚点不需要改手势代码。

> 注：`horizontal_offset_m` **当前不存在**，是本期的全新字段。`SteamVrConfig` 需新增 `#[serde(default)]` 字段，`hmd_matrix` 从硬编码 `x = 0.0` 改为读取它；旧配置默认 0.0，行为不变。

#### 抓取方式

首版建议：**右手射线 + 平面命中**。

- 右控制器 `tracked_device_index_for_controller_role(RightHand)`；
- 控制器前向（局部 `-Z`）发射射线；
- 与面板所在平面求交；
- 命中点落在面板宽高范围内 → 可抓取；
- 抓住后，每帧用新的射线命中点与上一帧命中点的差值移动面板。

备选：**近距离抓取**。

- 手柄距离面板中心 < `near_radius_m`（默认 0.35m）时可抓；
- 适合面板在手臂范围内的场景，不依赖射线精度；
- 可在配置里用 `mode = "ray" | "near"` 切换，默认 `ray`。

#### 防误触与锁定

- `output.steamvr.gesture.locked` 默认 `true`。锁定时完全不读取/不响应拖拽输入。
- **锁定状态属于配置**：桌面设置、全局快捷键、VR 手势三条路径都必须写回 `output.steamvr.gesture.locked`（经 `update_and_persist_config`）。
- 解锁方式（已确认）：
  1. **默认：桌面设置页勾选 + 全局快捷键 `toggle_steamvr_lock`**；
  2. **VR 内组合手势为可选**，默认关闭，由 `gesture.unlock_via_vr_gesture = false` 控制；开启后建议双手 trigger 同时按住 1.5 秒，带一次震动反馈。
- **VR 内解锁组合要加约束**：双手 trigger 在双持/双扳机游戏里很容易误触。开启该可选功能时，只有 pointer 命中面板（或面板最近可见）才接受解锁组合，并加 1s 冷却。
- 拖拽激活组合（已确认默认 `both_grips`）：
  - **必须 pointer 命中面板**（或近场抓到面板）才允许 arming，否则双 grip 在双持游戏里误触率过高；
  - 双手 grip 同时按住 250ms → 进入「移动模式」，短震动；
  - 之后由右手射线/近场拖动；
  - 松开任一手 → 结束并持久化；
  - 这样单手握持/游戏中的普通 grip 不会直接拖面板。
- 可在配置中改为 `right_grip` / `right_trigger`，给不需要严格防误触的用户使用。
- 拖动开始/结束/锁定切换都给一次 haptic（`trigger_haptic_pulse`，1000–1500us）。
- 面板因 `hide_on_silence_secs` 淡出隐藏时无法命中：文档需写明「先产生一条字幕再抓取」；本期不实现 VR 内召唤手势。
- **pointer 光标纳入 3C 首版（已确认）**：第二个 overlay，32x32 圆点，跟随射线命中点；抓取时变色。
  - pointer 需要独立 overlay key/name（如 `...subtitle.pointer`），并设置 `set_sort_order` 高于字幕面板，否则可能被面板遮住；pointer 本身不要设为 interactive。

#### 拖动增量

不要直接把「手柄世界位置」当作面板位置，使用射线命中点增量：

```
每帧：
  hit = intersect(controller_ray, panel_plane)
  if hit == None: 保持拖动状态但不移动（射线移出面板）
  if first_frame: prev_hit = hit
  delta_world = (hit - prev_hit) * sensitivity
  prev_hit = hit

  world / hmd 模式分别把 delta_world 应用到面板位置
```

- `sensitivity` 默认 1.0，范围 0.2–3.0。
- 单帧位移限制（如 0.25m），避免追踪丢失/射线接近平行时面板瞬移。
- 射线与平面夹角过小时（`|dot(dir, normal)| < 0.1`）跳过本帧。
- 命中点必须在面板矩形内（可加 5–10% 边距），否则视为移出，停止移动但不退出拖动。
- 退出拖动时只写回最终位置，避免每帧写配置。

### 4.3 坐标与数学

OpenVR `HmdMatrix34_t` 是 **3x4 行主序**：前三列是旋转/缩放，第 4 列是平移；控制器前向是局部 `-Z`。需要一个小的 3x4 矩阵辅助模块（不引入新依赖）：

```rust
// src/output/steamvr/gesture.rs
pub struct Mat3x4(pub [[f32; 4]; 3]);

impl Mat3x4 {
    pub fn transform_point(&self, p: [f32; 3]) -> [f32; 3];
    pub fn rotation_transpose_mul(&self, v: [f32; 3]) -> [f32; 3];
    pub fn multiply(&self, rhs: &Mat3x4) -> Mat3x4; // H * L
}

pub fn controller_forward(m: &Mat3x4) -> [f32; 3] {
    [-m.0[0][2], -m.0[1][2], -m.0[2][2]]
}

pub fn ray_plane_intersection(
    ray_origin: [f32; 3],
    ray_dir: [f32; 3],
    plane_point: [f32; 3],
    plane_normal: [f32; 3],
) -> Option<[f32; 3]>;
```

HMD 模式：

- 当前面板世界变换 `W = H_hmd * L`，其中 `L` 是 `hmd_matrix(config)` 的 3x4 矩阵。
- 把 `delta_world` 转成 HMD 局部增量：`delta_local = R_hmd^T * delta_world`。
- 新偏移：
  - `horizontal_offset_m = start_local.x + delta_local.x`
  - `height_offset_m = start_local.y + delta_local.y`
  - `distance_m = start_distance - delta_local.z`（因为前向是 -Z）
- 每帧可以用当前 HMD 的旋转做转换，面板持续跟随头部；如果希望拖动时世界稳定，也可以冻结起始 HMD 姿态，松手后再换算回 HMD 局部。首版建议使用当前姿态，避免松手时跳变。

World 模式：

- 起始世界位置 `P0 = config.world_position`；
- 每帧 `P = P0 + Σdelta_world`；
- 只改位置，`world_rotation_deg` 不变。

面板尺寸：

- 物理宽 `width_m`；
- 物理高 = `width_m * (texture_height / texture_width)`（渲染纹理的 texel aspect 默认为 1.0）；
- 需要在 VR 线程保存最近一次渲染的纹理尺寸，供命中测试使用。
- 曲面面板首版按中心切平面近似；`curvature` 较大时在文档中说明命中精度下降。

写入范围：

- 所有写回字段必须 clamp 到 `validate()` 的区间：`distance_m ∈ [0.2, 10]`、`height_offset_m ∈ [-2, 2]`、`horizontal_offset_m ∈ [-2, 2]`、`world_position` 每轴 `[-100, 100]`。
- 原因：主线程用 `update_and_persist_config` 落盘，内部会先 `validate()`；超范围的拖动值会导致保存失败并弹错，面板位置不持久化。
- HMD 模式若拖动后 `distance_m` 贴近 0.2m 或 10m，可选在 UI 上提示“已到边界”。
- World 模式的 `world_position` 是 Standing 绝对坐标；SteamVR 重新居中原点后，面板会随之偏移，这是现有行为，需在文档说明。

### 4.4 线程与配置持久化

保持现有线程模型，只加输入与拖动状态：

```text
VR 线程（33ms）
  ├─ poll SteamVR events
  ├─ 读 revision / config
  ├─ poll controller (Standing)
  ├─ 若 gesture.enabled && !gesture.locked：
  │    ├─ 组合键状态机（arming / dragging）
  │    ├─ 射线命中 + 更新本地 config 副本
  │    └─ apply_transform（使用本地 config）
  ├─ 渲染 / 上传纹理
  └─ 松手：设置 pending_pose + notify
```

关键点：

- **拖动期间不写 `Shared.config`**。VR 线程用本地 config 副本渲染，避免和主线程的 `apply_config` 竞争。
- **拖动期间必须绕过现有的 revision 节流**：当前 `session()` 只有在 `revision != last_revision` 时才调用 `apply_transform`；拖动时 revision 不会变化，若不处理面板不会移动。应把 transform 应用改为「每帧无条件执行（或 `dragging || retry_due`）」，纹理渲染/上传仍只在内容或配置 revision 变化时执行，避免每帧做 cosmic-text 布局。
- 拖动期间刷新 `last_activity`，避免 `hide_on_silence_secs` 在拖动中把面板淡出。
- `Shared` 增加 `config_epoch: AtomicU64`，`apply_config` 每次 +1。拖动开始时记录 epoch；如果中途 epoch 变化（用户在设置页改了参数/切换配置档），立即取消拖动，不写回。
- 松手时把最终值放进 `pending_pose: Mutex<Option<SteamVrPoseUpdate>>`，并 `notify` 主线程。
- 主线程现有 `outputs.status_notified()` 循环中增加：
  1. `take_steamvr_pose_update()`；
  2. **先 clamp 到 validate 区间**，再 `update_and_persist_config` 写入相关字段（`distance_m` / `height_offset_m` / `horizontal_offset_m` / `world_position`）；
  3. `apply_config(&config.output)` 同步回 VR sink；
  4. `emit_config` / `emit_output_status`。
- 只持久化松手后的最终值，不做每帧落盘；如果落盘失败，内存值仍生效并 emit error。
- 如果拖动期间 SteamVR 断开、tracking 失效、Dashboard 打开或锁定状态变化：取消拖动，不写回。
- **3A 退出移动模式时必须显式调用 `UpdateActionState` 把 `nPriority` 归 0（或提交空 action set）**，不能只依赖 SteamVR 在应用退出时清理；否则可能残留卡键。
- `config_epoch` 必须与内容 `revision` 分开：`publish` 也会递增 revision，不能拿 revision 当 epoch；`apply_config` 递增 epoch，`publish` 不递增。
- `ApplicationType`（Background/Overlay）由启动时配置决定，不在拖动路径动态切换；运行期改这项配置时提示重启应用（见 §4.1 限制 5）。

### 4.5 配置设计

```toml
[output.steamvr]
# hmd 模式水平偏移（米）；正数向右
horizontal_offset_m = 0.0

[output.steamvr.gesture]
# 启用手势移动。默认关闭：避免所有 Full 用户启动即轮询手柄并尝试 Input 2.0

# VR 内手势解锁（可选，默认关闭）。默认只允许桌面设置/全局快捷键解锁

unlock_via_vr_gesture = false
# 拖拽激活组合：both_grips | right_grip | right_trigger
# 默认 both_grips（已确认），但必须 pointer 命中面板才允许 arming
# （实现见 §4.2；若命中约束未实现，默认改为 right_grip）
grab = "both_grips"
# 抓取方式：ray | near
mode = "ray"
# 位移灵敏度
sensitivity = 1.0
# 显示射线命中光标（第二个小 Overlay，需独立 key/name + 更高 sort_order）
pointer = true
# 抓取/松手/锁定切换时震动
haptics = true
# near 模式的抓取半径（米）
near_radius_m = 0.35
# 移动模式下是否尝试屏蔽游戏输入（3A，纳入 0.3.0；需要 SteamVR Input 2.0 + app 注册 + 实验设置）
# 只绑定 grip/trigger，不动摇杆/菜单；默认关闭，由用户显式开启
# SteamVR 实验设置只检测并提示，不自动修改
block_game_input = false
```

> 字段说明：`horizontal_offset_m` 是本期新增的 `SteamVrConfig` 字段（旧配置缺省 0.0，行为不变），不是手势子段的一部分；`gesture` 是新的嵌套结构，需要 `Default` 实现。

`AppConfig::validate()` 增加：

- `horizontal_offset_m ∈ [-2, 2]`（新字段，无旧配置迁移风险）
- `distance_m / height_offset_m` 继续使用现有范围（`distance_m ∈ [0.2, 10]`、`height_offset_m ∈ [-2, 2]`）
- `sensitivity ∈ [0.2, 3]`
- `near_radius_m ∈ [0.05, 2]`
- `grab ∈ {both_grips, right_grip, right_trigger}`
- `mode ∈ {ray, near}`
- `unlock_via_vr_gesture` / `block_game_input` / `pointer` / `haptics` / `enabled` / `locked` 为布尔
- `block_game_input` 默认 `false`；开启后运行期检测 SteamVR 设置与 action manifest 是否可用，不可用时降级为「不屏蔽」并在状态里说明；只绑定 grip/trigger
- `world_position` 继续限制在 `[-100, 100]`

`output.steamvr.gesture.*` 与 `horizontal_offset_m` 默认热字段，`is_restart_required` 返回 `false`；但 `ApplicationType` 若改为按配置决定，则 `gesture.block_game_input` 的首次开启可能需要提示重启（由 spike 结论决定）。

### 4.8 需求三测试与验收

纯函数单测（所有平台可跑）：

- `Mat3x4::multiply` / `transform_point` / `rotation_transpose_mul`；
- 射线与平面平行 → `None`；
- 射线反向 / 命中在面板外 → 拒绝；
- hmd 局部增量与 world 增量的换算；
- 单帧位移限制；
- `GestureState` 状态机：锁定、arming 超时、双 grip、松手、epoch 变化取消；
- 写入值 clamp：`distance_m` / `height_offset_m` / `horizontal_offset_m` / `world_position` 超范围时被夹到边界；
- `horizontal_offset_m` 缺省 0.0 与 `hmd_matrix` 的 x 偏移映射（防止回归到硬编码 0）。

手工验收（3C）：

1. 锁定开启：任意手柄操作不移动面板。
2. 快捷键解锁后：射线命中面板 → 出现 pointer；按住组合 → 面板跟随；松手 → 位置保持并写入配置。
3. `anchor = hmd`：拖动后 `distance_m / height_offset_m / horizontal_offset_m` 改变，重启后仍生效。
4. `anchor = world`：拖动后 `world_position` 改变，旋转不变，重启后仍生效。
5. 拖动到 `distance_m` / `horizontal_offset_m` 边界：值被 clamp，不出现保存失败弹错。
6. 拖动中在设置页改参数 → 拖动取消，不覆盖用户的新参数。
7. SteamVR 断开/重连 → overlay 恢复到最后持久化的位置。
8. 运行 SteamVR 游戏时，默认锁定下无误触；解锁后只有明确组合才会移动。
9. Dashboard 打开时无法拖动（可接受，给出文档说明）。
10. 面板因静音隐藏时，先产生一条字幕再抓取。

手工验收（3A，仅当决策门通过）：

11. SteamVR 实验设置关闭 → 设置页显示「未开启」；3C 拖动仍可用，不残留卡键。
12. manifest 缺失 / `steamvr.vrmanifest` 未注册 → 状态显示可读错误，不崩溃。
13. 进入移动模式 → 游戏侧 grip/trigger 被压制、摇杆/菜单正常；退出后立即恢复。

### 6.1 macOS-only 开发机的验证策略

开发机只有 macOS 时，M5–M9 不能只依赖本机的 `--features steamvr`：非 Windows 下 `imp.rs` 会走 `stub.rs`，**绿灯不代表真实 SteamVR 代码被编译**。分层验证：

| 层级 | 命令 | 能证明什么 |
| --- | --- | --- |
| macOS 默认/可选 feature 单测 | `cargo test --locked --all-targets --features osc,steamvr` | 跨平台逻辑、配置、UI、`gesture.rs` 纯函数；steamvr 仍是 stub |
| Windows 交叉编译/静态检查 | `cargo xwin clippy --locked --all-targets --features extras --target x86_64-pc-windows-msvc -- -D warnings` | **真实 Windows `imp.rs` / `input.rs` 的类型、API、cfg 与 lint**；不执行 Windows 测试 |
| Windows 测试执行 | GitHub Actions `windows-latest` 的 `cargo test --features extras` | Windows 链接与测试执行；由 push/PR 触发 |
| 真机 VR | Windows + SteamVR + 头显 | overlay 拖动、pointer、输入屏蔽、卡键恢复、Dashboard 行为；**只能在 Windows 真机人工验收** |

前置（本地交叉检查）：`rustup target add x86_64-pc-windows-msvc`、`rustup component add llvm-tools`、Ninja，以及一个把 MSVC `lib.exe` 参数转给 `llvm-ar` 的 `llvm-lib` shim。工具放 `.pi/gvs-tools/bin`（`.pi/` 已在 `.gitignore`），不进入发布产物。

约束：

- 交叉 `clippy/check` 只做编译与 lint，**不链接、不运行**；最终仍需 Windows CI 的 `cargo test --features extras` 与真机验收。
- 不得因为 macOS 的 stub 绿灯就宣称 3C/3A 已验证；未在 Windows 编译/运行的项必须在报告里单列。
- 如果 CI Windows 失败，在 macOS 上按日志修复后重新 push；GVS 的 batch 完成不等于可合并。

## 9. 待确认问题

### 已确认（已写入计划）

- **3A 纳入 v0.3.0**；3C 与 3A 都按 0.3.0 交付。
- 默认抓取组合 **`both_grips`**，但必须 pointer 命中面板才允许 arming。
- **默认桌面/快捷键解锁；VR 内手势解锁可选且默认关闭**（`unlock_via_vr_gesture = false`）。
- **pointer 光标纳入 3C 首版**。
- `gesture.locked` 通过任何路径切换都**写回配置**。
- 「桌面端」只过滤浮窗字幕；历史窗口与 popover 显示全部源；`enabled = false` 保留历史，删除源才消失。
- `horizontal_offset_m` 采用**右正**（x 轴 +）。
- SteamVR 资源用 **`include_bytes!` 内嵌**，首次解压到**活动配置文件所在目录**下的版本化子目录（便携模式即 exe/config；默认是 OS 用户配置目录），不可写时回退 `data_local_dir()`。
- 3A **只屏蔽 grip/trigger**；SteamVR 实验设置**只检测/提示**，不提供一键开启。
- 快捷键录制期间**暂停所有全局快捷键（含退出）**。
- 变更日志采用 **git-cliff 自动生成 + 手写升级说明**（后者进 release body 与 `docs/UPGRADING.md`）。

### 仍需确认（实现/ spike 后拍板）

1. **`Background` vs `Overlay`**：spike 证明 `Background` 拿不到 global priority 时，是否改用 `ApplicationType::Overlay`？这会改变 SteamVR 启动/保持行为，且切换需重启应用。
2. **决策门失败时的替代路线**：若 manifest 注册/默认 bindings 在 zip 发布目录下无法稳定工作，选路线 B（全屏蔽）、改 Overlay，还是调整 0.3.0 范围？
3. **`gesture.enabled` 默认值**：当前计划默认 `false`（安全、零副作用）。3A 纳入 0.3.0 后是否改为默认 `true`，让用户开箱即用？
4. **`block_game_input` 默认值**：当前计划默认 `false`（需用户显式开启）。是否改为默认 `true`（移动模式自动屏蔽 grip/trigger）？
5. **资源解压目录与清理**：默认放「活动配置文件所在目录」的 `steamvr/<version>/`（便携模式就是 exe 旁的 `config/`；默认是 OS 用户配置目录），不可写回退到 `data_local_dir()`。是否接受？旧版本子目录保留一代还是立即清理？
6. **升级说明范围**：`docs/UPGRADING.md` 需要覆盖到哪些内容——只写 0.2.x → 0.3.0 的默认值/行为变化，还是也写 SteamVR 实验设置、manifest 注册、已知限制与回滚方式？

## 10. 建议的首个提交范围

为了尽快拿到可验证的中间结果，建议第一个 PR 只做：

- M0 + M1 + M2 的后端部分：配置字段、`ChannelFilter`、`display_lines_for`、`OutputManager::publish` 改造、`main.rs` 三视图；

第二个 PR 做设置页表格和需求 2（**必须包含录制前暂停全局快捷键**）；第三个 PR 做 Phase S1 spike；3A（Phase S2/M9）在 0.3.0 内单独排期，不阻塞 1/2/3C 的合并，但**发布前必须完成或按 §9 拍板替代方案**。
